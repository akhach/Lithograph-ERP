# 1. Purpose

This document defines the implementation sequence for the Projects module.

Projects connect:

```text
Client
   ↓
Project
   ↓
Orders
```

Orders are implemented in the next phase.

During this phase, Projects must support:

```text
Project creation

Project Business IDs

Client relationship

Project status

Project dates

Project Team

Owner

Assignee

Participants

Observers

Project Workspace
```

---

# 2. Main Goal

After this phase, Lithograph ERP must be able to:

```text
Create a Project for a Client

Assign Employees to the Project

Identify Owner and Assignee

Add Participants and Observers

Edit Project information

Change Project status

Filter/search Projects

Open a Project Workspace
```

---

# 3. Module Boundary

Projects owns:

```text
projects.projects

projects.project_members
```

Projects references:

```text
clients.clients

employees.employees

auth.users
```

Projects does not own those entities.

# 17. Numbering Rules

```text

Unique

Immutable

Year-based
```

---

# 18. Yearly Reset

Project sequence resets for each calendar year.

Example:

```text
PRJ-2026-000001
PRJ-2026-000002
```

then:

```text
PRJ-2027-000001
```

---

# 19. Business Year Source

The year comes from controlled backend current time.

Do not trust:

```text
Frontend year

User-entered year
```

---

# 20. Concurrency Safety

Concurrent Project creation must not create duplicate Business IDs.

Never use:

```text
SELECT MAX(...) + 1
```

# 32. Composite Primary Key


# 33. Multiple Roles per Employee

```text

→ Owner
```

# 34. Duplicate Same Role

```text

Participant
```

being inserted twice for the same Project.

Composite PK prevents it.

# 38. Observers

# 51. One Owner Database Protection

Where practical, create a PostgreSQL partial unique index equivalent to:

```text
UNIQUE project_id
WHERE project_role = 'owner'
```

---

# 52. One Assignee Database Protection

Likewise:

```text
UNIQUE project_id
WHERE project_role = 'assignee'
```

---

# 53. Application + Database Protection

Owner/Assignee uniqueness should be protected by:

```text
Application validation
+
Database constraint
```

Application gives useful errors.

Database protects integrity.

---

# 54. Client Delete Behavior

Project must not disappear because a Client is deleted.

Normal Client physical deletion is not supported.

Use restrictive safe FK behavior.

---

# 55. Employee Delete Behavior

Project Member history must not cascade-delete the entire Project.

Normal Employee physical deletion is not supported anyway.

---

# 56. Project Member Delete Behavior

Removing a Project Member deletes only the relationship row.

It does not delete:

```text
Project

Employee
```

# 179. Project Team Inheritance Rule

The next Orders phase must use:

```text
Order
→ Project
→ Project Team
```

Do not copy Project Team rows into Orders.

---

# 180. No Order-Specific Team

Version 1 must not create:

```text
orders.order_members
```

or:

```text
order_owner_id

order_assignee_id
```

---

# 181. No Project Financial Columns

Do not store:

```text
selling_total

cost_total

profit
```

on Project.

These will be derived from Orders.

---

# 182. No Project Order Count Column

Do not store:

```text
order_count
```

merely for convenience.

Derive/query it where needed.

---

# 183. No Project Client Duplication

Project stores one:

```text
client_id
```

Orders later derive Client through Project.

---

# 184. No Project Checklist

Checklist belongs to Order.

---

# 185. No Project Calculator

Calculator belongs to Order.

---

# 186. No Project Folder Links in V1

Folder Links belong to Order.

---

# 187. No Automatic Project Status Changes

Creating or completing Orders must not automatically change Project status unless a future explicit rule is added.

---

# 188. No Automatic Employee Removal

Employee deactivation must not automatically rewrite Project Team history/current relationships.

---

# 189. Future Project Extensions

Potential future additions may include:

```text
Project-level files

Project-level notes/history

Project financial dashboards

Project templates

Project custom fields

Project status history
```

They are not Version 1 requirements.

---

# 190. Project Simplicity Rule

Before adding a Project field, ask:

```text
Is this information truly about the Project,
or does it belong to an Order?
```

If it describes individual production work, it probably belongs to Order.

---

# 191. Final Projects Principle

The Projects module should answer:

```text
Which Client is this work for?

What is the Project?

Who is responsible for it?

Who participates in it?

What is its current status?
```

It provides the stable container into which Orders will be created.

The central rule is:

```text
Project defines context and team.

Order defines the actual work.
```
